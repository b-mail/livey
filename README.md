# Livey — 라이브 데모 수정 에이전트

**3일 걸리던 대답을, 미팅 자리에서 바로.**

화면에 떠 있는 라이브 데모를 채팅으로 수정 요청하면, **서로 다른 해석의 A안·B안**을
격리된 샌드박스에서 동시에 만들어 열어볼 수 있는 URL로 돌려준다.

데모 영상 → https://youtu.be/BdR_JZkfID8

---

## 왜 만들었나

### 왜 화면 하나 바꾸는 데 왕복 3일이 걸릴까?

| | | |
|---|---|---|
| **0일차 고객사 미팅** | "이 화면 이렇게 바꿀 수 있나요?" | 지금의 답은 "개발팀과 내부적으로 확인한 후에 말씀드리겠습니다" |
| **+2~3일 왕복** | 고쳐서 다시 보여주기까지 | 그 사이 고객의 세일즈 온도는 떨어진다 |
| **+2~3일 재수정** | "생각했던 거랑 다르네요" | 해석이 하나뿐이라 한 번에 맞을 확률이 낮다 |

질문 한 마디의 값이 3일. 그리고 그 3일은 우리가 아니라 고객이 기다린다.

### 3일이 지나는 동안 무엇이 사라지는가

- **고객의 모멘텀** — 미팅에서 올라온 관심은 회신까지 걸린 시간에 비례해 식는다.
  그 자리에서 답이 나왔다면 성사됐을 대화가 다음 미팅 안건으로 밀린다.
- **한 번으로 안 끝난다** — 해석이 하나뿐이라 첫 수정본이 빗나가면 왕복이 또 한 번.
  화면 하나 확정하는 데 두세 번이 예사다.
- **팀의 리소스** — PO와 개발자가 붙어서 만들어 내는 결과물은 결국 "해석 하나"다.
  버려지는 왕복마다 그 비용이 다시 든다.

느린 게 문제가 아니라, **느린 만큼 기회가 닫힌다**는 게 문제다.

### 근본 원인 — Sales가 FDE가 될 순 없을까?

| As Is | To Be |
|---|---|
| 코딩 역량이 없음 | 서로 다른 해석을 **동시에** 살려두기 |
| 고객의 요청을 이해하는 능력은 있지만, 기술적으로 가능한 요청인지 판단하기 어려움 | 나란히 놓고 고객이 직접 비교하기 |
| | 고르는 순간이 곧 확정되는 구조 |

Sales에게 즉시 빌드되는 데모는 강력한 무기가 된다.

## 해법 — 확인 후 회신 대신, 지금 열어보세요

### 90초

요청 한 줄에서 열어볼 수 있는 공개 URL 배포까지 걸리는 시간.

1. 입력창에 자연어로 수정 요청
2. 샌드박스가 동시에 기동
3. 서로 다른 안이 실제로 도는 URL로

고객은 샌드박스 결과물을 그 자리에서 고른다. **회신 메일은 없다.**

> "AI가 코드를 고친다"가 아니다. 그건 이미 흔하다.
> **여러 갈래를 동시에 살려두고 비교하게 만드는 것.**
> 그리고 이건 격리된 머신을 순식간에 여러 개 띄울 수 없으면 불가능하다.

---

## 구조 — 오케스트레이터 하나, 샌드박스 여럿

```
입력창          오케스트레이터        변형 A · 보수적  → 샌드박스 A → 정적 서버      결과 카드
자연어    ──▶   asyncio.gather  ──▶                                          ──▶  요약 + URL
수정 요청                            변형 B · 과감형  → 샌드박스 B → 정적 서버      + 진행 상태
```

오케스트레이터가 원본 HTML과 요청을 LLM에 병렬로 넘기고, 돌아온 HTML을 각각
샌드박스에 올려 정적 서버를 띄운 뒤 프리뷰 URL을 돌려받는다.

레인은 `orchestrator.py`의 `LANES` 딕셔너리로 정의된다. 현재 프로토타입은
**A(보수적) · B(과감형) 2레인**이고, 항목을 추가하면 그대로 N레인으로 늘어난다.

| 레인 | 접근 | 프롬프트 스타일 |
|---|---|---|
| **A안** | 보수적 | 요청을 최소 변경으로 반영한다. 기존 구조를 유지한다. |
| **B안** | 과감형 | 요청 의도를 확장 해석해 정보를 더한다. |

```
orchestrator.py        # FastAPI + asyncio.gather, A/B 레인 병렬 실행
static/index.html      # 콘솔 (데모 슬롯 + 채팅 + 내비게이션 + 설명 패널)
static/livey-logo.png  # Livey 로고
demo/settlement-dashboard.html  # 샘플 정산 대시보드 (드래그 앤 드롭용)
variants/1/{a,b}.html  # 1번째 요청 — A안 파이 차트 / B안 도넛 차트
variants/2/{a,b}.html  # 2번째 요청 — A안 파트너 칩 필터 / B안 툴바 필터+합계 행
```

## 실행

```bash
pip install -r requirements.txt
python orchestrator.py
# → http://localhost:8787
```

`demo/settlement-dashboard.html`을 화면에 끌어다 놓고 채팅에 수정 요청을 입력하면 된다.

### 화면 구성 (Vercel 대시보드 스타일)

- **전체 화면 = 데모 슬롯** — 단일 HTML 파일을 **드래그 앤 드롭**(또는 클릭 선택)하면
  `/api/demo`로 등록되어 이 자리에 라이브 데모로 로드된다. 새로고침하면 지워진다.
- **우측 = AI 채팅** — 수정 요청을 자연어로 입력. 채팅 안에서 A안·B안의
  단계 진행(변형 생성 → 샌드박스 기동 → 서버 실행 → 준비 완료)이 표시된다.
- **생성 완료 후** — 상단 중앙에 `[원본 · A안 · B안]` 내비게이션이 나타난다.
- **A안/B안 선택 시** — 하단에 AI의 자연어 설명 패널이 열리고 데모는 축소된다.
  **위로 스크롤**하면 설명이 플로팅 카드로 접히며 데모가 전체화면이 된다.
  (아래로 스크롤하거나 플로팅 카드를 클릭하면 다시 도킹)

### 모드

- **mock (기본)** — `variants/`의 변형을 로컬에서 서빙하고 단계 진행을 시뮬레이션.
  키 없이 즉시 동작.
- **daytona** — `DAYTONA_API_KEY` 설정 시 진짜 샌드박스를 띄운다
  (`deploy_daytona()` — 레퍼런스 구현).

LLM 연동은 `generate_variant()` 함수 하나만 교체하면 된다
(원본 HTML + 요청 + `prompt_style` → 수정된 HTML).

## 승인 → 실행: 고객이 고른 안이, 그대로 티켓이 된다

**고객이 고른 안 + 승인 한 번** → 쓰던 협업 도구로 그대로 흘러간다.

| | 하는 일 | 내용 |
|---|---|---|
| **Slack** | 담당 채널 스레드로 | 요청 원문 · 고른 안 · 프리뷰 URL이 한 메시지로 |
| **Linear** | 이슈 자동 생성 | 제목 · 본문 · 링크까지 채워진 채로 백로그에 |
| **Jira** | 티켓 자동 생성 | 쓰던 워크플로 그대로, 담당자와 기한만 붙이면 끝 |
